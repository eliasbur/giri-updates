# /experiment

Manage research experiments with structured documentation. Create experiment folders, log progress, track sub-experiments, and generate summary READMEs.

## Usage

```
/experiment create <slug> --hypothesis "<what you're testing>"
/experiment create <slug> --from-task "<task-file.md>"

/experiment log <slug> "<entry text>"
/experiment log <slug> --file "<path-to-notes.md>"

/experiment status <slug>                      # Generate/update summary README
/experiment status <slug> --include-results    # Include preliminary results

/experiment list                               # List all experiments
/experiment show <slug>                        # Show experiment structure

/experiment add-sub <parent-slug> <sub-slug>   # Create nested sub-experiment
/experiment complete <slug> --conclusion "<findings>"
```

## What You Must Do When Invoked

### Step 1 - Validate experiment slug

Experiment slugs must be:
- Lowercase with hyphens (kebab-case)
- 3-50 characters
- Descriptive but concise
- Unique within `docs/experiments/`

Check for conflicts:
```bash
ls docs/experiments/ 2>/dev/null | grep -i "<slug>"
```

If conflict exists:
- Suggest alternative (add date, version number, or more specific name)
- Ask user to confirm before proceeding

### Step 2 - Create experiment structure

For `/experiment create <slug>`:

```bash
mkdir -p "docs/experiments/<slug>"
mkdir -p "docs/experiments/<slug>/sub-experiments"
mkdir -p "docs/experiments/<slug>/results"
mkdir -p "docs/experiments/<slug>/assets"
```

Create core files:

**1. `experiment.md`** - Main experiment description:
```markdown
---
slug: <slug>
created: <ISO-date>
modified: <ISO-date>
status: proposed|active|paused|completed|abandoned
hypothesis: <one-sentence hypothesis>
tags: []
---

# <Human-Readable Title>

## Hypothesis

<Clear statement of what you're testing. Example: "Using Apptainer 
multi-stage builds will reduce container size by 40% compared to 
single-stage builds while maintaining functionality.">

## Background

Why this experiment matters. What problem does it solve? What 
observation led to this hypothesis?

## Experimental Design

### Variables

- **Independent**: What you're changing
- **Dependent**: What you're measuring
- **Controlled**: What you're keeping constant

### Setup

```bash
# Commands to set up the experiment
# (fill in as you go)
```

### Metrics

How will you measure success?
- Metric 1: <description, target value>
- Metric 2: <description, target value>

## Procedure

Step-by-step what you'll do:

1. Step one
2. Step two
3. Step three

## Sub-Experiments

| Slug | Description | Status |
|------|-------------|--------|
| (none yet) | | |

## References

- [ ] Paper/doc 1
- [ ] Paper/doc 2

---

*Generated by manage-experiments skill*
```

**2. `progress.md`** - Dated log entries:
```markdown
# Progress Log

## <YYYY-MM-DD> - Initial Setup

- [ ] Setup completed
- [ ] Baseline measurements taken

Notes:
<Initial observations>

---

## <YYYY-MM-DD> - First Run

- [ ] First experiment run
- [ ] Data collected

Notes:
<What happened>

---

*(New entries added at top)*
```

**3. `results.md`** - Findings and data:
```markdown
# Results

## Summary

<Will be populated when experiment completes>

## Data

### Run 1: <date>

| Metric | Value | Notes |
|--------|-------|-------|
| | | |

### Run 2: <date>

| Metric | Value | Notes |
|--------|-------|-------|

## Analysis

<Interpretation of results>

## Conclusion

<Final conclusion when experiment completes>
```

**4. `README.md`** - Human-readable summary (generated by `/experiment status`):
```markdown
# <Title>

**Status**: <badge>  
**Created**: <date>  
**Last updated**: <date>

## At a Glance

> **Hypothesis**: <one sentence>
> 
> **Current status**: <2-3 sentence summary>

## Quick Links

- [Full experiment details](experiment.md)
- [Progress log](progress.md)
- [Results](results.md)
- [Sub-experiments](sub-experiments/)

## Latest Update

<Most recent progress entry, summarized>

## Key Findings

<Bullet points of important discoveries>

---

*Auto-generated README. Edit experiment.md, progress.md, or results.md directly.*
```

### Step 3 - Suggest experiment name (if user didn't provide)

When user invokes without specific slug, suggest based on:

**From hypothesis**:
```
hypothesis: "Multi-stage builds reduce container size"
→ suggest: multi-stage-build-optimization

hypothesis: "Slurm array jobs speed up parameter sweep"
→ suggest: slurm-array-parameter-sweep
```

**From task** (if `--from-task`):
```
task: "Optimize Apptainer build time"
→ suggest: apptainer-build-time-optimization
```

**From context** (conversation):
```
User: "I want to test if GPU utilization improves with batch size 64"
→ suggest: gpu-batch-size-64-test
```

Always present suggestion and ask for confirmation:

```
💡 Suggested slug: `<suggested-slug>`

Based on: <hypothesis/task/context summary>

Proceed with this slug? (yes/modify/cancel)
```

### Step 4 - Log progress entries

For `/experiment log <slug> "<entry>"`:

1. **Read current `progress.md`**
2. **Parse date** from entry or use today's date
3. **Insert at top** of file (after header, before first `---`)
4. **Update modified date** in `experiment.md` frontmatter

Format for new entry:
```markdown
## <YYYY-MM-DD> - <Short Title>

<entry text>

**Files changed**:
- `path/to/file.py`: description

**Commands run**:
```bash
<relevant commands>
```

**Observations**:
- Key observation 1
- Key observation 2

---

```

For `/experiment log <slug> --file "<notes.md>"`:
- Read the file
- Extract content
- Format as progress entry
- Insert at top of `progress.md`

### Step 5 - Generate status README

For `/experiment status <slug>`:

1. **Read all experiment files**:
   - `experiment.md` - hypothesis, design
   - `progress.md` - latest entries
   - `results.md` - any findings
   - `sub-experiments/*.md` - count and status

2. **Generate summary sections**:

**At a Glance**:
```markdown
> **Hypothesis**: <from frontmatter>
> 
> **Status**: <from frontmatter>
> 
> **Progress**: <X> days active, <Y> log entries, <Z> sub-experiments
```

**Latest Update**:
- Extract most recent entry from `progress.md`
- Summarize to 2-3 sentences
- Include date

**Key Findings**:
- Scan `results.md` for completed sections
- Extract bullet-worthy discoveries
- If none: "No significant findings yet"

3. **Write `README.md`** (overwrite existing)

4. **Report to user**:
```
✅ README updated for: <slug>

📊 Summary:
  - Status: <status>
  - Days active: <count>
  - Log entries: <count>
  - Sub-experiments: <count>

📄 Files:
  - experiment.md (hypothesis & design)
  - progress.md (<entries> entries)
  - results.md (<findings> findings)
  - README.md (auto-generated summary)

🔗 View: docs/experiments/<slug>/README.md
```

### Step 6 - Create sub-experiments

For `/experiment add-sub <parent> <child>`:

1. **Create child structure** (same as Step 2)
2. **Link to parent**:
   - Add to parent's `sub-experiments/` table
   - Add `parent: <parent-slug>` to child's frontmatter
3. **Create symlink or reference** in `sub-experiments/` folder

### Step 7 - Complete experiment

For `/experiment complete <slug> --conclusion "<findings>"`:

1. **Update `experiment.md`**:
   - Set `status: completed`
   - Update `modified` date
2. **Update `results.md`**:
   - Fill in `## Conclusion` section
   - Add conclusion text
3. **Generate final README**:
   - Include conclusion in summary
   - Mark as completed
4. **Archive assets**:
   - Move important outputs to `assets/`
   - Reference in results

## Experiment Status Lifecycle

```
proposed → active → paused → active → completed
                    ↓
                abandoned
```

- **proposed**: Hypothesis defined, not yet started
- **active**: Currently running, collecting data
- **paused**: Temporarily stopped (blocked, waiting)
- **completed**: Concluded, findings documented
- **abandoned**: Stopped without conclusion (document why)

## Examples

### Example 1: Create experiment from hypothesis

```
/experiment create multi-stage-build-optimization --hypothesis "Multi-stage Apptainer builds reduce container size by 40% while maintaining functionality"
```

Creates:
```
docs/experiments/multi-stage-build-optimization/
├── README.md
├── experiment.md
├── progress.md
├── results.md
├── assets/
└── sub-experiments/
```

### Example 2: Log progress

```
/experiment log multi-stage-build-optimization "Built baseline single-stage container. Size: 2.4GB. Build time: 8 minutes."
```

Appends to `progress.md` with today's date.

### Example 3: Generate status

```
/experiment status multi-stage-build-optimization
```

Updates `README.md` with current summary.

### Example 4: Add sub-experiment

```
/experiment add-sub multi-stage-build-optimization gpu-vs-cpu-build
```

Creates nested experiment for comparing GPU vs CPU builds.

### Example 5: Complete experiment

```
/experiment complete multi-stage-build-optimization --conclusion "Multi-stage builds reduced container size by 45% (2.4GB → 1.3GB) with identical functionality. Build time increased by 2 minutes but caching mitigates this for iterative development."
```

## Best Practices

### Writing Good Hypotheses

✅ **Good**: "Using X will improve Y by Z%"
✅ **Good**: "Method A produces more accurate results than Method B"
❌ **Bad**: "Let's try X and see what happens"
❌ **Bad**: "Improve performance" (too vague)

### Logging Progress

- **Be specific**: Include exact commands, versions, parameters
- **Timestamp everything**: Use ISO dates (YYYY-MM-DD)
- **Note surprises**: Unexpected results are often most valuable
- **Link to commits**: Reference git commits for reproducibility

### Organizing Results

- **Raw data**: Keep in `results/` or link to external storage
- **Visualizations**: Save to `assets/`, reference in results.md
- **Analysis**: Write narrative in `results.md`, not just tables

### When to Split into Sub-Experiments

Create sub-experiments when:
- Testing multiple independent variables
- Exploring different approaches to same problem
- Need to compare A/B/C variants systematically

## Anti-Patterns

❌ **No hypothesis**: Just running things without clear question
❌ **Undocumented failures**: Only logging successes
❌ **Scattered notes**: Progress in random files, not progress.md
❌ **No conclusion**: Experiments that never get marked complete
❌ **Overly complex**: Too many variables changed at once
❌ **No metrics**: Can't quantify success or failure
