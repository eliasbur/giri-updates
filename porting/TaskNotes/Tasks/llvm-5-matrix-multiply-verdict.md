## Goal

Decide, with evidence that survives the counter-argument below, whether `matrix_multiply-seq`'s
16-extra / 1-missing diff is a legitimate `FAIL-EXPECTED` or an unfixed defect — and make the suite's
one remaining `[FAIL]` mean exactly one agreed thing.

## Why this task exists

`llvm-5-seq-variant-failures` (merged as `3945134`) did the hard part well. The
`PostDominanceFrontier::calculate` segfault was root-caused to `Frontiers` being a `DenseMap` whose
references `calculate()` holds across recursive insertions, fixed by making it a `std::map`
(reference-stable, matching LLVM 3.4's `DominanceFrontierBase`), and **verified by reverting the fix
and watching the 13 `Could not find Control-dep` warnings reappear**. That is the standard this
project asks for.

The verdict it then filed on the remaining diff is not held to the same standard.
`porting/TestAudit/llvm-5.0.2/matrix_multiply-seq.md` says:

> **Root cause:** LLVM 5.0.2 generates different IR than LLVM 3.4, producing different basic block
> layout and instruction numbering; golden file is tied to a specific compiler build
> […] The slicing criterion (`matrix_mult:285`) resolves to a different instruction in LLVM 5.0.2's
> IR […] This difference cannot be resolved without changing the golden file, the criterion, or the
> compiler version.

Four problems with that, in descending order of importance.

### 1. The pthread variant refutes the general claim

`matrix_multiply-pthread` is the same program family, compiled by the same clang 5.0.2, sliced by
the same Giri, against a golden (`ans-inst-pthread.txt`, 60 lines) generated by the same LLVM 3.4
that produced the seq golden — and it **matches exactly**. It was verified clean in
`llvm-5-test-fixes` and re-verified in `llvm-5-seq-variant-failures`.

So "a 3.4-vintage golden cannot be reproduced under 5.0.2 because the IR differs" is false as a
general statement on this branch. Something specific to `matrix_multiply-seq` has to carry the
verdict, and it has not been named.

### 2. The instruction the criterion resolves to was never identified

The seq task specified the check and it was not done:

> `llvm-dis` the `.all.bc` and identify instruction #285 of `matrix_mult` in the 5.0.2 build.
> Compare against what the golden slice implies the criterion should be.

The report asserts the criterion "resolves to a different instruction" without saying which
instruction it resolves to, or which one it should have been. That is the difference between a root
cause and a restatement of the symptom.

### 3. 18 of 19 golden lines are present — which argues *against* criterion drift

The golden is 19 lines (`56 90 97 113 119 120 121 122 123 129 131 133 137 139 141 145 147 149 154`).
The actual slice contains 18 of them; only line 97 (`dprintf("\n")`) is absent. A criterion that
resolved to a genuinely different instruction would not preserve 95% of the expected slice.

What the diff actually looks like is **over-inclusion**: 16 extra lines, and the report itself
groups them as "loop headers, boundary calculations, loads, multiplications, stores" (75-86, 92-94)
plus "main function data setup" (155-157, 165). Extra loop headers and boundary calculations are the
signature of too many *control-dependence* edges being added — and control dependence is exactly
what this task's own fix just changed, from "frontier corrupt, 13 edges missing" to "frontier
computed". The possibility that the frontier is now over-producing was never considered. Before the
fix the slice was too small; after it, it is too large. Neither state is evidence that the golden is
unreachable.

### 4. The report's numbers do not close

> Actual output contains 35 unique source lines. Golden file contains 19 lines.

18 golden lines present + 16 extra listed = 34, not 35. One line in the actual output is
unaccounted for. In a report whose entire verdict rests on characterising the diff, that gap has to
be closed before the characterisation can be trusted.

### Also missing: the suite result itself

The DoD box "Full suite re-run and the per-test result recorded" is ticked, but no suite line or
per-test table appears in the note, in `SUMMARY.md`, or in the reports. Re-run it and record it.

## What to do

### 1. Identify the criterion instruction — this is the cheap decisive step

```bash
docker exec giri-mm llvm-dis /giri/test/matrix_multiply/matrix_multiply-seq.all.bc -o - \
  | sed -n '/define .* @matrix_mult(/,/^}/p'
```

Count instructions the way `Giri.cpp:296-303` counts them — `inst_iterator` over the function, every
instruction including PHIs and the terminator, not source lines and not counting labels. Record:

- the total instruction count of `matrix_mult`;
- instruction #285 verbatim, with its `!dbg` source line;
- whether that line is one of the golden's 19.

If #285 is the store of a computed output cell (what the golden implies the criterion is, mirroring
`matrixmult_map 138` in the pthread variant), the criterion is **correct** and root cause 1 is dead —
the diff is then a slicing defect and this task escalates to fixing it.

### 2. If and only if #285 looks wrong, quantify the drift

Sweep nearby indices and find whether some `matrix_mult N` reproduces the golden exactly:

```bash
for n in $(seq 260 310); do
  echo "matrix_mult $n" > /tmp/crit.txt
  # run the -dgiri stage with -criterion-inst=/tmp/crit.txt, diff the .slice.loc against the golden
done
```

A hit is a precise, checkable result: "3.4's #285 is 5.0.2's #N, drift of N-285 instructions,
`FAIL-EXPECTED` confirmed". No hit anywhere in the range is evidence the criterion is not the
explanation at all. Do this in a scratch directory — **do not modify
`test/matrix_multiply/criterion-inst-seq.txt`**.

### 3. Test the over-inclusion hypothesis

For at least the 16 extra lines' basic blocks, determine why they entered the slice: a data
dependence from the criterion, or a control dependence via `findExecForcers`. `-trace-cd=false`
(`lib/Giri/Giri.cpp:55`) disables control-dependence tracing — running with it off and comparing the
two slices separates the two sources cheaply. If the extra lines are control-dependence-sourced,
compare what `calculate()` now produces for those blocks against what the frontier *should* be, and
say whether `std::map` fixed the crash while leaving the computation wrong.

### 4. File the verdict

Rewrite `matrix_multiply-seq.md`'s root-cause section to whichever answer the evidence supports.
`FAIL-EXPECTED` is still available — but it now has to explain why the pthread variant's 3.4-vintage
golden reproduces exactly and the seq one cannot. If instead this is a defect, fix it or escalate it
with the same evidence standard the DenseMap fix met.

## How to build and test

Nothing is built or tested in the devcontainer (`AGENTS.md` → "Containers — two kinds"):

```bash
docker build -t giri:5.0.2 .
docker run -d --name giri-mm --cpuset-cpus=0-3 -v $PWD:/giri -w /giri giri:5.0.2 sleep infinity
docker exec giri-mm bash -lc 'source /giri/utils/build.sh'
```

Rebuild with `make -j$(nproc) -C /giri/build`, not `docker build`. Name the variant explicitly on
every `make` command line — the image sets `TEST_PARALLELISM=seq` and the Makefiles' `?=` yields to
it:

```bash
docker exec giri-mm make -s -C /giri/test/matrix_multiply TEST_PARALLELISM=seq DEBUGFLAGS=
docker exec giri-mm make test -s -C /giri/test/matrix_multiply TEST_PARALLELISM=seq DEBUGFLAGS=
```

## Traps

- **The crash is fixed; do not re-litigate it.** `Frontiers` is a `std::map` for a reason that was
  proven by revert-and-reproduce (`include/Utility/PostDominanceFrontier.h:28`). If you touch
  `calculate()`, the 13-warnings-reappear check is your regression test.
- Do not "fix" the diff by editing the golden or the criterion file. That is the escalation trigger,
  not the fix.
- The `bbid` / `lsid` / `prtrace` targets pipe into `view -` (vim) and hang under `docker exec` —
  run `opt … -dump-bbid=true` / `-dump-lsid=true` or `/giri/build/bin/prtrace <file>` directly.
- `-debug` / `-debug-only=` are no-ops on the no-asserts 5.0.2 toolchain, as are Giri's own
  `assert()`s (`Release` CMake build).
- A traced binary never dies by a signal — Giri's runtime handles the fatal signals and exits with
  the signal *number* (`runtime/Giri/Tracing.cpp:253-256`). See `llvm-5-harness-signal-detection`.
- Evidence goes in the report, not in `test/_test_logs/` — that directory is gitignored scratch that
  the next suite run overwrites.
- Live-shared checkout: `git add` explicit paths only, never `git add -A`.
